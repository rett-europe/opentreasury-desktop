## Review — perf(#39-c): Playwright perf-budget gate

Thanks for the careful scope here, @copilot — the harness shape (3 cold launches → median, OT_DATA_DIR isolation, OT_SEED=none, virtualised-row-aware selector, debug doc) is exactly the right contract for #39-c. Lint and typecheck are clean, vitest baseline is unchanged (1 pre-existing flake in `MovementsScreen.bulk.test.tsx` is unrelated and passes in isolation).

I attempted to reproduce locally end-to-end and uncovered one **blocking** issue. Requesting changes.

---

### 🔴 Blocking — gate measures nothing because Electron loads the wrong `userData` directory

**File:** `tests/e2e/movements-perf.spec.ts:62`

```ts
const app = await electron.launch({
  args: [path.join('dist', 'main', 'index.js')],   // ← this
  env: { ...process.env, OT_DATA_DIR: 'perf-events', OT_SEED: 'none' },
});
```

When Playwright launches Electron with `args: ['dist/main/index.js']`, Electron treats the argument as a **script path**, not an app root. It never reads our project `package.json`, so `app.getName()` falls back to the default `"Electron"` and `app.getPath('userData')` resolves to `%APPDATA%\Electron`, not `%APPDATA%\opentreasury-desktop`.

I verified this empirically with a tiny diag spec (using Playwright's `app.evaluate`):

```
[diag main] {"userData":"C:\\Users\\perocha\\AppData\\Roaming\\Electron",
             "OT_DATA_DIR":"perf-events", "name":"Electron"}
[diag main] expected event log path: ...\Electron\perf-events\events.ndjson  exists: false
```

Meanwhile `npm run perf:seed` (correctly) writes to `%APPDATA%\opentreasury-desktop\perf-events\events.ndjson`. So the Electron under test boots against an **empty** event log every time.

Symptom in the renderer (confirmed by polling the DOM after the nav click):

```
Income €0.00  Expense €0.00  Net €0.00  Transactions 0
```

i.e. `loadAll()` resolves with zero rows → `<Table>` is never mounted → `'table.ot-table tbody tr:not([aria-hidden="true"])'` never matches → `waitForSelector` times out at `BUDGET_MS * 10 = 5000ms` → test fails on run #1, every time. **The gate does not actually exercise the MovementsScreen perf path; it just measures "how long until we give up looking for a row that will never exist".**

**Fix:** launch Electron against the project root so it picks up our `package.json` (`name: opentreasury-desktop`, `main: dist/main/index.js`):

```ts
const app = await electron.launch({
  args: ['.'],
  env: { ...process.env, OT_DATA_DIR: 'perf-events', OT_SEED: 'none' },
});
```

I made this single-line change locally and re-ran the spec. The gate now produces real numbers:

```
[perf] run 1/3: 698 ms
[perf] run 2/3: 754 ms
```

Two related observations follow naturally once the gate actually measures:

### 🟠 Likely-blocking — global `timeout: 120_000` is marginal once the gate works

**File:** `playwright.config.ts:25`

With the launch fixed, on my Windows machine each Electron cold-launch + boot + measure + close took ~40 s. Three runs blow past the 120 s test timeout (run 3 never completed in my repro). On `xvfb` Ubuntu runners the per-launch cost may be similar.

Bump to `timeout: 240_000` (or have the spec call `test.setTimeout(240_000)` explicitly), and consider also raising the inner `waitForSelector` cap from `BUDGET_MS * 10` (5 s) — it's fine for the assertion to be the median, but a single cold-cache run can legitimately go past 5 s.

### 🟠 Likely — 500 ms budget is tighter than the actual signal

Once the gate measures correctly, my two completed local samples were 698 ms and 754 ms. That's a Windows desktop with a warm dev environment — expect Ubuntu CI runners to land *higher*, not lower. Per `docs/perf/playwright-gate.md` the plan is to recalibrate to `observed_median × 1.5` after a week of `main` data, but with the current 500 ms ceiling the gate will fire on day 1 — there will be no week of data to collect.

Two options, your call:
- (preferred) Land the budget at `1500 ms` from day 1 and keep the "tune to `median × 1.5` after one week" plan; OR
- Land `BUDGET_MS = 500` only after collecting one CI sample on `main` to confirm Linux runners are dramatically faster than my Windows box.

### 🟡 Nit — selector is intentionally position-based, but the doc string is slightly off

**File:** `tests/e2e/movements-perf.spec.ts:28`

The comment says "stable across i18n locales" — true and a good design choice. Worth adding a one-liner `aria-label="Primary"` anchor to make it slightly more robust against future sidebar restructuring:

```ts
const MOVEMENTS_NAV_BTN =
  'nav[aria-label="Primary"] > div:first-child > ul > li:nth-child(2) > button';
```

Non-blocking, but cheap insurance.

### 🟡 Nit — `playwright.config.ts:31` no `workers: 1`

`fullyParallel: false` already serialises within a project, but you don't have multiple projects — adding `workers: 1` makes the perf-isolation contract explicit at the config level (and protects against someone introducing a second project later). Fine to leave as-is.

### Architecture / scope: looks good

- CI gate scoped to `push` on `main` only is the right call for a slow + initially-noisy gate.
- `xvfb-run` + `playwright install --with-deps chromium` for the system deps is the right pattern.
- `OT_DATA_DIR` + `OT_SEED=none` cleanly isolate the perf dataset from the dev seed.
- Median-of-3 is fine; documenting `RUNS` must stay odd is a nice touch.
- `docs/perf/playwright-gate.md` is exactly what we want — owner, threshold rationale, debug playbook, and the recalibration policy.

Once the launch bug is fixed and the budget/timeout are tuned to a value the gate can actually pass on the first `main` push, this is ready to land.
